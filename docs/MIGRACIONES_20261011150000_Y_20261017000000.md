# Análisis de las migraciones `20261011150000` y `20261017000000`

Fecha: 2026-10-12. Candidato: `95144a17`. **Este documento no aprueba ninguna migración**: la decisión es del propietario (CODEOWNER de `/backend/prisma/`). Todo lo medido se hizo en PostgreSQL 16 temporal y aislado; no se tocó ninguna base real. Las pruebas están en `backend/test/migraciones-control-arranque.postgres.integration.ts` (14 pruebas).

## 1. `20261011150000_precio_aprobacion_producto`

| Pregunta | Respuesta (evidencia) |
|---|---|
| SQL real | `ALTER TABLE productos ADD COLUMN` ×5 (`precio_aprobado BOOLEAN NOT NULL DEFAULT false`, `precio_aprobado_por`, `precio_aprobado_at`, `precio_modificado_por`, `precio_modificado_at`); un `UPDATE productos` que marca `precio_aprobado=true`, `precio_aprobado_por='LEGADO_MIGRACION'` y `precio_aprobado_at=CURRENT_TIMESTAMP` **solo** donde `activo = true AND precio_venta > 0`; `CREATE INDEX` sobre `(tenant_id, precio_aprobado)` |
| Tablas y registros afectados | Solo `productos`, todas las empresas. El `UPDATE` toca **solo** los productos activos con precio positivo |
| ¿Modifica datos históricos? | **Sí, en el sentido de la aprobación**: los productos que hoy se venden quedan «aprobados por legado» para no dejar de venderse. No toca existencias, costos ni precios (prueba: foto de `id|nombre|precio|costo|stock|reservado|activo` idéntica antes y después) |
| Consecuencia comercial | Los productos activos **sin** precio (0) y los **inactivos** quedan pendientes: **no se pueden vender hasta que un administrador apruebe el precio** (comprobado en el ensayo: venta de un producto heredado con precio = 201; sin precio = 4xx) |
| Compatibilidad con el esquema existente | Aditiva. `ADD COLUMN` con valor constante por defecto no reescribe la tabla (PostgreSQL ≥ 11). Bloqueo breve de la tabla durante el `CREATE INDEX` (no concurrente): imperceptible con miles de productos, pero conviene hacerlo fuera de horario |
| Comportamiento ante error | Cada migración corre en una transacción implícita de un solo envío. Si falla (p. ej. la columna ya existe), no cambia ningún dato: prueba «ejecución parcial previa» → los datos quedan idénticos, la migración queda registrada como **incompleta** y `migration-safe` bloquea el arranque (`MIGRACION_INCOMPLETA`) hasta recuperarla |
| Ejecutarla dos veces | Con Prisma: la segunda vez no hace nada (ya figura aplicada; la marca de tiempo de aprobación no cambia). Ejecutando el SQL a mano dos veces: falla en la primera sentencia (`column already exists`) y **no** reescribe las aprobaciones. **Riesgo:** ejecutar solo el `UPDATE` suelto, sin las columnas, sobrescribiría `precio_aprobado_por` de productos que un humano aprobó después; no lo haga |
| Recuperación | Sin datos nuevos que perder: reversión manual (documentada en el propio archivo) = `DROP INDEX` + `DROP COLUMN` de las cinco columnas, y restaurar la copia previa si algo más falló. Migración incompleta: quitar la columna suelta, `prisma migrate resolve --rolled-back 20261011150000_precio_aprobacion_producto` y volver a desplegar (probado de punta a punta, sin pérdida) |

### El conflicto de los dos contenidos

Hay **dos archivos distintos con el mismo nombre**. Prisma identifica una migración por nombre y guarda el SHA-256 de su contenido; si el contenido cambia, es otra migración «distinta» para el control de integridad.

| Versión | SHA-256 (inicio) | Dónde está | Diferencia |
|---|---|---|---|
| **Candidata** | `8885a35a928bbd2d…` | candidato `95144a17` y las ramas apiladas | `WHERE "activo" = true AND "precio_venta" > 0` |
| Alterna | `d84f7934cb433c7b…` | `claude/keen-goldberg-62o7f1`, `claude/forja-compras-proveedores` (y copia de prueba en `backend/test/fixtures/20261011150000_variante_keen.sql.txt`) | `WHERE "precio_venta" > 0` (también aprueba los **inactivos**) |

La única diferencia material es la cláusula `activo = true`: con la alterna, un producto dado de baja con precio quedaría aprobado y volvería a venderse **sin revisión** al reactivarse. Por eso la candidata es la conservadora.

**Qué pasa si un entorno aplicó la otra versión** (probado): `migration-safe` marca `CHECKSUM_DISTINTO` y **se niega a arrancar y a migrar** (`verify`, `startup`, `deploy`; `inspect` devuelve el error). No corrompe nada, pero el servicio no levanta. **Resolución** (plan completo en `docs/PLAN_RECONCILIACION_MIGRACION_20261011150000.md`): decisión del propietario y, si existe ese caso, reconciliar el checksum con un procedimiento aprobado; nunca editar la migración publicada.

**Cómo saber el estado de cada base (solo lectura):** `backend/scripts/estado-base-solo-lectura.sql` (sección 3 y 6) y `backend/scripts/inspeccion-solo-lectura-migracion-20261011150000.sql`. `main` **no contiene** esta migración, así que una producción que corre `main` debería **no** tener ninguna de las dos; solo un entorno de pruebas que haya desplegado las ramas de keen/forja podría tener la alterna.

| Tablas y registros afectados | Solo la restricción de `operaciones_contingencia`. **No borra ni modifica filas ni columnas** (prueba: huella MD5 de todas las filas idéntica antes y después) |
| ¿Modifica datos históricos? | No. Tampoco puede fallar por datos existentes: la regla nueva es **más débil** que la anterior para los estados terminales y **igual** para el resto, así que toda fila válida antes lo sigue siendo |
| Compatibilidad | La tabla existe solo si se aplicó `20261011000000_pos_contingencia_offline`; en una producción basada en `main` es **una tabla nueva y vacía** al migrar (la contingencia está apagada) |
| Comportamiento ante error / interrupción | `DROP` y `ADD` van en el mismo envío: si algo falla entre ambos, la transacción se revierte y **la restricción anterior queda intacta** (prueba con error forzado tras el `DROP`) |
| Ejecutarla dos veces | Idempotente: `DROP … IF EXISTS` + `ADD`; tras la segunda ejecución hay exactamente **una** restricción con la misma definición (prueba) |
| Bloqueo | `ACCESS EXCLUSIVE` breve sobre `operaciones_contingencia` mientras revalida las filas; con la tabla vacía o pequeña es inmediato |
| Invariantes que conserva (probados) | `REVISION`/`RECIBIDA`/`APLICADA` siguen exigiendo `total > 0` y `efectivo >= total`; `RECHAZADA` admite importes incoherentes pero no negativos; una `RECHAZADA` nunca tiene `venta_id` (restricción de `20261016`) |
| Recuperación | Reversión manual **no automática**: `backend/prisma/rollback-manual/20261017000000_contingencia_rechazos_importe_incoherente.sql`. Solo es posible si no existen filas `RECHAZADA`/`RESUELTA_MANUAL` con importes que la regla vieja prohíbe; si existen, restaurar la copia previa |
| Decisión pendiente | **Aprobación de CODEOWNERS (@Nelosama)** y, si lo desea, opinión de NEXUS (`docs/NEXUS_SOLICITUD_REVISION_F5_20261017.md`). Con la contingencia apagada la migración no tiene efecto operativo, solo deja el esquema listo |
